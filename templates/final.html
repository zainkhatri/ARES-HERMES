Sigma Platform — What to Know

Terms are in context — read this once and they'll stick when you use them in the demo.

The core concept: live connection, not an extract
Most BI tools — Tableau included — work on an extract: they copy a snapshot of your data out of the warehouse into their own cache, then query that cache. The snapshot goes stale the moment it's taken. You have to schedule refreshes.

Sigma uses a live connection — every action you take generates SQL that runs directly against Snowflake, the CDW (Cloud Data Warehouse), in real time. No copy, no cache, no staleness. This is called query pushdown — the compute stays in the warehouse, not in Sigma's servers.

Plugs Electronics pain this solves: their Tableau extracts time out on large POS datasets. With Sigma, 4.6M rows is just a query. Snowflake handles it.
Alpha Query — why Sigma feels instant
Not every action in Sigma hits Snowflake. Sigma has an optimization called Alpha Query — for operations like sorting, filtering already-returned data, or UI interactions that don't change the underlying query, Sigma answers from its local cache instead of re-running the warehouse query. You'll see "Alpha Query" in the query history when this happens. It's a performance optimization — good thing to mention if a technical person asks why it's so fast.
How the data is structured — terms you'll hear
  • Fact table — the main transaction table. PLUGS_ELECTRONICS_HANDS_ON_LAB_DATA is a fact table. Each row = one transaction line item. This is also called the grain of the data — the grain here is one POS line item per row.
  • Dimension — a column you use to slice and filter. Store Region, Product Type, Customer Name are dimensions. They describe what the transaction was.
  • Measure — a numeric column you aggregate. Revenue, Profit, Quantity are measures. They describe how much.
  • Aggregate — rolling up rows into a summary using SUM, COUNT, AVG. When you group by Region and sum Revenue, you're aggregating. Same as a pivot table.
  • Drillthrough — clicking on an aggregated value to see the underlying detail rows. This is exactly what you do in Act 1 when you click the South bar and drill down. Tableau doesn't let you do this freely — Sigma does.
  • Derived metric / calculated column — a column you create with a formula, like Profit = Revenue − COGS. It doesn't exist in the raw data — Sigma calculates it on the fly via SQL.
Workbook — the main object
  • A workbook contains pages. Each page can have data tables, charts, pivot tables, controls.
  • Columns work like Excel — type a formula in the header, it applies to every row.
  • Grouping = drag a column to the group area = GROUP BY in SQL = pivot table in Excel.
  • Live edit = multiple people can be in the same workbook simultaneously, like Google Sheets but on warehouse data.
  • Child element = a chart or pivot table that inherits from a parent table. When you filter the parent, the child updates.
  • Page control = a filter that's been promoted to the dashboard level and applies to all elements on the page.
CSV Upload + Joining
  • Upload a CSV into a workbook — Sigma writes it to Snowflake automatically (that's why the training says "save your review data — this will write your spreadsheet data back to Snowflake").
  • Then join it to warehouse data on a shared column — the join key. In the demo, Brand is the join key between the reviews CSV and the POS data.
  • A join combines two tables on a matching column, like a VLOOKUP in Excel that works across millions of rows.
  • The lookup in Module 3 (pulling Avg Rating into the input table by Brand) is a specific type of join — you're looking up one value per Brand from the reviews table.
AI Features — know these three
  • Ask Sigma — natural language → Sigma builds the query. Good for demos, but don't lead with it. It can feel like a gimmick. Lead with spreadsheet UX first.
  • Formula Assistant — describe what you want, get a formula. Like Copilot for the column bar.
  • AI Column (the one to demo) — CallNumber() calls an LLM (large language model) running inside Snowflake Cortex — Snowflake's native AI runtime. Each row gets scored. Runs inside the CDW, so data never leaves the warehouse. This matters for compliance — no third-party API call, no data leaving the perimeter.
Writeback — the differentiator
  • Users type values into a Sigma Linked Input Table and those values get pushed back to a Snowflake table. This is writeback.
  • Most BI tools are read-only — they query data, they don't write it. Writeback turns Sigma into a data app, not just a BI tool.
  • Full audit trail — every change is logged: who changed it, when, what the value was before. This matters for compliance and for building trust.
  • Use cases: pricing recommendations, demand planning, scenario modeling (what-if analysis), approval workflows.
Governance + Security — terms for the CIO
  • Row-level security (RLS) — filters data by user identity. A store manager only sees their store's rows. Defined once in the data model, enforced everywhere.
  • Column-level security (CLS) — hides specific columns from specific roles. Salary data visible to HR only.
  • Data model — a governed, reusable layer that defines your metrics (what "revenue" means, what "margin" means) so every team is calculating the same thing. Also called a semantic layer — it sits between the raw warehouse tables and the business users.
  • OAuth — users authenticate to Snowflake with their own credentials, not a shared service account. Every query is attributable to a person.
  • Private Link — encrypted connection between Sigma and Snowflake over a private network. Traffic never hits the public internet.
  • Version tagging — publish a specific version of a workbook so users always see a stable, approved view. Rollback if something breaks.
  • SOC 2 Type II — the security certification Sigma holds. Means an independent auditor has verified their security controls. CIOs ask about this.

How to Pivot When You Don't Know Something

Never say "I don't know" and stop. Always bridge to something you do know, or redirect to them.
If a question throws you:
"That's a great question — why does that matter to you specifically?"
Gets them talking. Buys you time. Often surfaces the real concern, which you can answer.
If you don't know a specific feature or spec:
"I want to make sure I give you the accurate answer on that — let me confirm and follow up. What I can tell you is [related thing you do know]."
Integrity > bullshitting. They respect the honesty. Always bridge to something real.
If a technical question is too deep:
"That's getting into the weeds of the implementation — I'd want to loop in our technical team to walk through that architecture with you. What I can show you is how it behaves from a user perspective."
Then go back to the demo. Don't get stuck in a technical rabbit hole.
If the demo breaks:
"This is exactly why I always keep a backup tab open — let me switch over."
Keep talking while you recover. Silence is worse than narrating. A light joke is fine.

SQL — Conversational Only

You're never writing SQL in the demo. But a BI lead will ask. Know what Sigma is doing under the hood and how to explain it.

The big picture first: SQL is the language databases speak. Sigma translates every drag, click, and formula you do into SQL automatically and fires it at Snowflake. The result comes back and Sigma renders it. You never write SQL — but everything you do generates it.

The term for this is query pushdown — the computation happens inside the CDW, not on Sigma's servers. This is why it scales to 4.6M rows without breaking a sweat.
SQL conceptWhat it meansIn the demo
SELECT Choose which columns to return — like deciding which columns are visible in your spreadsheet Every workbook column is a SELECT
WHERE Filter rows before returning them — like an Excel filter, but it runs in the warehouse on all 4.6M rows Page controls, product family filter in Module 3
JOIN Combine two tables on a shared column (the join key) — like a VLOOKUP that works across millions of rows. A LEFT JOIN keeps all rows from the left table even if there's no match on the right. Joining the reviews CSV to POS data on Brand
GROUP BY Bucket rows into groups, then calculate something for each group. Dragging Store Region to the group area = GROUP BY Store Region. Same thing Excel pivot tables do. Grouping by Brand in Module 3, grouping by Store Region in Module 1
Aggregate function A calculation across a group of rows — SUM (total revenue), COUNT (number of transactions), AVG (average rating), CountDistinct (unique customers). Sigma auto-picks SUM when you drag a measure to a chart. Sum([Profit]), Avg of Rating, CountDistinct([Customer Name])
ORDER BY Sort the results — highest profit first, lowest rating first Sorting brands by Avg Rating in the input table
Three terms that come up in BI conversations:
  • Schema — the structure of tables in the database. Which columns exist, what type they are (text, number, date). When someone asks "what's in your schema?" they mean "what tables and columns do you have?"
  • Star schema — the most common data warehouse design. One central fact table (transactions) surrounded by dimension tables (product, store, customer). The POS data in Snowflake follows this pattern.
  • Data latency — how old is the data? Tableau extracts can be 24+ hours stale. Sigma's live connection = zero latency. Whatever happened this morning is in the query.
"Sigma pushes every interaction down into Snowflake as SQL — your data team can actually inspect the exact queries Sigma generates. Nothing is computed outside your warehouse."
If a BI lead asks to see the SQL Sigma generated:
"Sigma has a query inspector — your analysts can see exactly what SQL ran for any workbook action. Great for validating what's happening under the hood and for auditing."
(In Sigma: kebab menu on any table → "View Query". Know where this is before the demo.)

How to Talk in the Room

Treat them as real prospects, not interviewers. Adam said this is the most important thing. The panel will hold questions until the end, but they're in character. Stay in character too. If you break the fourth wall, the demo falls apart.

Pacing

  • Slower than you think. You'll want to rush. Don't.
  • Pause after every demo moment. Let it land. Ask a question.
  • Silence is okay. Don't fill it with filler words.
  • If you finish a section early, ask a discovery question instead of moving on.

Transitions — say these out loud until they're natural

  • "Let me show you what that looks like in the product." → opens Sigma from slides
  • "I want to pause here — this is the merchandiser view. Analytics Manager, this is actually where your team saves the most time. Let me show you why." → persona pivot mid-demo
  • "Now here's where Sigma does something no other tool does." → entering writeback
  • "That's a great point — why does that matter to you specifically?" → any time you're thrown
  • "Before I move on — does this resonate with what you're seeing today?" → check-in mid-demo

Multi-persona management

  • Address each persona by role, not name. "For a merchandiser, this means..." "From an analytics manager perspective..."
  • When you show something relevant to one persona, acknowledge the others: "And I know for the CIO in the room, the governance story matters more than the UI — let me show that in a second."
  • Don't ignore anyone for more than 3-4 minutes. They'll disengage.

Owning the room

  • You're the only Sigma person there (AE is sick). You control the pace, the agenda, the close.
  • If someone asks a question mid-demo: answer it, then say "let me keep going and we'll come back to this." Don't let one question derail the flow.
  • Energy matters. If you're excited about what you're showing, they feel it. If you're nervous, they feel that too.
  • The opening line sets the tone. Say it before you open the laptop.
